# Expense Agent Execution Flow

This document is the code-level walkthrough for the first Expense Agent milestone. It is intentionally written as a developer debugging guide: each step lists the function, inputs, outputs, and the next step.

## 1. Entry point

### `ExpenseAgent.resolve(expense_id)`

**Input**

```text
expense_id: str
```

**Does**

- Loads the expense using `ExpenseService.get_by_business_id()`.
- Creates `ExpenseAgentState`.
- Builds the initial LLM message history.

**Output**

```text
ExpenseAgentState
messages[]
```

**Next** → LLM call.

---

## 2. LLM call

### `AsyncOpenAI.chat.completions.create()`

The agent sends:

```text
model
messages
 tools
 tool_choice="auto"
 temperature=0
```

### `messages`

Conversation history for the current run:

```text
SYSTEM  → agent instructions
USER    → "Resolve expense EXP-..."
ASSISTANT → tool call, when the model requests one
TOOL    → result returned by our application
ASSISTANT → next tool call or final decision
```

### `tools`

Machine-readable descriptions of functions the LLM may request. The model does not execute Python functions itself.

Current tools:

```text
get_expense(expense_id)
search_expense_policy(query)
```

### `tool_choice="auto"`

Means the model chooses whether to:

```text
call a tool
OR
return the final decision
```

This is what makes the loop dynamic instead of a fixed sequence.

**Output**

OpenAI assistant message containing either:

```text
tool_calls[]
```

or final text containing an `AgentDecision` JSON object.

**Next** → inspect `tool_calls`.

---

## 3. Tool decision

### `ExpenseAgent.resolve()`

Checks:

```python
if not tool_calls:
    final decision
else:
    execute requested tools
```

### Case A — no tool call

**Next** → `_parse_decision()`.

### Case B — tool call exists

**Next** → `_execute_tool()`.

---

## 4. Tool execution

### `ExpenseAgent._execute_tool(name, arguments, expense_id)`

**Input**

```text
name: tool name chosen by LLM
arguments: JSON arguments generated by LLM
expense_id: current expense
```

The function maps the model-generated tool call to an application method.

```text
get_expense
    ↓
ExpenseAgentTools.get_expense()

search_expense_policy
    ↓
ExpenseAgentTools.search_expense_policy()
```

The LLM cannot directly execute Python or access the database.

**Output**

A JSON-serializable dictionary containing the tool result.

**Next** → append a `role="tool"` message to `messages` and call the LLM again.

---

## 5. `get_expense()`

### `ExpenseAgentTools.get_expense(expense_id)`

**Input**

```text
expense_id
```

**Does**

Loads the current expense and returns structured business data, including:

```text
employee
manager
category
description
amount
currency
expense_date
status
documents
approvals
```

**Output**

JSON object safe to place into an LLM tool message.

**Next** → LLM decides whether another tool is required.

---

## 6. `search_expense_policy()`

### `ExpenseAgentTools.search_expense_policy(query)`

**Input**

```text
query: policy question generated by the agent
```

**Does**

Calls the existing `KnowledgeService.query()` rather than implementing another retrieval pipeline.

**Output**

```text
answer
sources[]
```

Each source includes document/chunk/page identifiers and text.

**Next** → LLM evaluates the policy evidence against the expense.

---

## 7. Repeat the loop

The agent continues:

```text
LLM
 ↓
tool call?
 ├── yes → execute tool → append tool result → LLM
 └── no  → final decision
```

Maximum rounds:

```text
MAX_TOOL_ROUNDS = 6
```

If the limit is reached, the run fails rather than looping indefinitely.

---

## 8. Final decision

### `_parse_decision(content)`

**Input**

```text
LLM final text
```

**Does**

Validates JSON using the Pydantic `AgentDecision` schema.

**Output**

```text
AgentDecision
```

Current allowed statuses:

```text
SUBMITTED
INFORMATION_REQUIRED
APPROVED
```

Current required actions:

```text
NONE
ADDITIONAL_INFORMATION
ADDITIONAL_DOCUMENT
MANAGER_DECISION
```

---

## 9. Application state vs LLM message state

There are two different forms of state.

### `ExpenseAgentState`

Application-owned state:

```text
expense
tool_results
evidence
missing_information
```

### `messages[]`

LLM conversation state:

```text
system
user
assistant tool calls
tool results
assistant final decision
```

The two should not be treated as interchangeable.

---

## 10. Logs to follow locally

The agent logs each major transition with the function name:

```text
ExpenseAgent.__init__
ExpenseAgent.resolve: start
ExpenseAgent.resolve: expense_loaded
ExpenseAgent.resolve: initial_messages_prepared
ExpenseAgent.resolve: llm_call_start
ExpenseAgent.resolve: llm_call_complete
ExpenseAgent._execute_tool: start
ExpenseAgent._execute_tool: complete
ExpenseAgent.resolve: final_decision
ExpenseAgent.resolve: max_tool_rounds_exceeded
```

The logs intentionally do not print full receipt contents, policy text, or employee details beyond the expense identifier and non-sensitive counts/status fields.

---

## 11. Current limitation

The current DocumentService stores uploaded PDFs and schedules processing, but the repository's PDF parsing step is not yet implemented. Therefore the agent can currently use:

```text
structured expense data
existing document/approval associations
policy search results
```

It cannot yet reason over the extracted content of a receipt PDF.

That is the next evidence milestone.
