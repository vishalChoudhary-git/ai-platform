# Expense Resolution — Current Architecture and Workflow

This document describes the Expense Resolution implementation currently present on `feature/expense-notifications`.

## 1. Business goal

The Expense Resolution Agent investigates an employee expense using submitted business data, parsed receipt evidence, and the applicable company policy. It can autonomously reach:

```text
APPROVED
INFORMATION_REQUIRED
```

When manager input is required, the agent advances the workflow to:

```text
INFORMATION_REQUIRED
required_action = MANAGER_DECISION
```

The agent does not make the human manager's final approval/rejection decision.

## 2. High-level flow

```text
POST /plugins/expenses
        |
        v
   Expense created
   status=submitted
        |
        v
 Background document processing
        |
        +--> Parse/chunk/embed receipt document
        |
        +--> Extract structured receipt evidence
        |       |
        |       +--> Redis evidence cache
        |
        v
 Expense Resolution Service
        |
        v
    Expense Agent
        |
        +--> get_expense()
        +--> get_expense_evidence()
        +--> get_expense_policy()
        +--> search_expense_policy() when needed
        |
        v
   AgentDecision
        |
        +--> APPROVED
        |       |
        |       +--> notify employee + manager
        |
        +--> INFORMATION_REQUIRED
                |
                +--> ADDITIONAL_INFORMATION
                |       |
                |       +--> notify employee only
                |
                +--> ADDITIONAL_DOCUMENT
                |       |
                |       +--> notify employee only
                |
                +--> MANAGER_DECISION
                        |
                        +--> create ExpenseApproval(PENDING)
                        +--> notify employee + manager
                        |
                        v
                POST /plugins/expenses/{expense_id}/approval
                        |
                        +--> approved → Expense APPROVED
                        +--> rejected → Expense REJECTED
                        |
                        +--> ExpenseApproval resolved
                        +--> notify employee + manager
```

## 3. Create expense API

### `POST /plugins/expenses`

The API accepts the expense data and one or more uploaded documents.

A new business identifier is generated by the system:

```text
EXP-XXXXXXXXXXXX
```

Currency defaults to `INR` when omitted from a new expense. Missing currency therefore does not trigger `additional_information`.

The request returns immediately with the current expense state. Document parsing and resolution happen asynchronously.

For an existing expense, the same endpoint can use:

```text
?expense_id=EXP-XXXXXXXXXXXX
```

to append new information or documents.

## 4. Document processing

Each submitted receipt is represented by the generic platform `Document` plus an Expense-specific `ExpenseDocument` association.

The platform document pipeline is responsible for:

```text
PDF
 ↓
parse
 ↓
chunks
 ↓
embeddings
 ↓
DocumentChunk
```

The Expense plugin then extracts normalized receipt evidence.

### `ExpenseEvidenceProcessor`

Typical evidence:

```json
{
  "document_type": "receipt",
  "merchant": "Green Leaf Cafe",
  "amount": "1350",
  "currency": "INR",
  "expense_date": "2026-08-18",
  "fields": {}
}
```

Evidence is currently stored as a Redis-derived artifact using an expense/document-specific key.

## 5. Company policy processing

Company policies are uploaded through the Expense-specific policy endpoint:

```text
POST /plugins/expenses/policies
```

The temporary development authorization uses the debug auth context. Future JWT authentication can replace that implementation without changing the policy API.

The policy lifecycle is:

```text
UPLOADED
   ↓
PROCESSING
   ↓
validated/normalized
   ↓
PUBLISHED
```

Published policy versions are immutable. A policy change creates a new version.

### `ExpensePolicyProcessor`

The processor:

```text
Policy PDF
 ↓
platform document parsing/chunking/embedding
 ↓
Policy rule extraction
 ↓
PolicyRule[]
 ↓
ExpensePolicySnapshot
 ↓
Redis cache
 ↓
PUBLISHED
```

Policy cache identity is based on immutable document checksum.

## 6. Expense Agent

### `ExpenseAgent.resolve(expense_id)`

The agent starts with:

```text
system instructions
user goal: Resolve expense EXP-...
```

The model receives tool definitions and uses:

```text
messages=messages
tools=tool_definitions
tool_choice="auto"
temperature=0
```

`tool_choice="auto"` allows the LLM to decide which investigation steps are necessary.

Current read-only tools:

```text
get_expense(expense_id)
get_expense_evidence(expense_id)
get_expense_policy(expense_id)
search_expense_policy(query)
```

The loop is capped at six tool rounds.

Important default:

```text
currency omitted → INR
```

Missing currency alone must never result in `required_action=additional_information`.

## 7. Example — normal expense

```text
Receipt: hotel/meals expense = INR 1,350
Policy: meals <= INR 3,000/day

Agent
 ↓
get_expense()
 ↓
get_expense_evidence()
 ↓
get_expense_policy()
 ↓
compare evidence to policy
 ↓
AgentDecision
 ↓
status=approved
required_action=none
```

The resolution service persists the decision to `expenses` and notifies the employee and manager.

No `ExpenseApproval` row is created because manager action is not required.

## 8. Example — manager decision required

```text
Receipt: hotel expense = INR 25,000
Policy: hotel <= INR 15,000

Agent
 ↓
get_expense()
 ↓
get_expense_evidence()
 ↓
get_expense_policy()
 ↓
policy threshold exceeded
 ↓
AgentDecision
 ↓
status=information_required
required_action=manager_decision
```

The resolution service then creates:

```text
ExpenseApproval
    expense_id = current expense
    approver_email = expense.manager_email
    status = pending
    reason = agent decision reason
```

Creation is idempotent for an existing pending manager approval.

The employee and manager are notified. The manager email includes the policy ID/version and applied rule when available in decision evidence.

## 9. Status API

### `GET /plugins/expenses/{expense_id}`

The client should use this endpoint to observe the workflow because the create request does not wait for parsing and agent evaluation.

The response includes:

```text
expense_id
status
required_action
decision_reason
decision_evidence
documents
approvals
```

`decision_evidence` is represented as a JSON list because one decision can contain multiple evidence items, such as a receipt finding and an applied policy rule.

## 10. Manager approval API

### `POST /plugins/expenses/{expense_id}/approval`

For the current development implementation, the manager is identified with:

```text
X-Debug-User-Email: manager@example.com
```

This temporary mechanism is intentionally replaceable by JWT authentication later.

Request body:

```json
{
  "decision": "approved",
  "reason": "Business travel was within the approved exception."
}
```

or:

```json
{
  "decision": "rejected",
  "reason": "The expense was not justified for the stated business purpose."
}
```

A rejection reason is required.

The endpoint validates that:

```text
expense.required_action == manager_decision
AND
pending ExpenseApproval exists for the requesting manager
```

On approval:

```text
ExpenseApproval → approved
Expense.status → approved
Expense.required_action → none
```

On rejection:

```text
ExpenseApproval → rejected
Expense.status → rejected
Expense.required_action → none
```

After either final manager decision, employee and manager notifications are sent.

## 11. Notification rules

Notifications are intentionally based on the workflow action, not only the high-level status.

```text
approved + none
    → employee + manager

information_required + additional_information
    → employee only

information_required + additional_document
    → employee only

information_required + manager_decision
    → employee + manager

rejected
    → employee + manager
```

For local Mailtrap testing, recipient messages are throttled using the configured delay to respect sandbox rate limits.

## 12. Important architectural boundaries

### Generic document platform

Owns:

```text
Document
Document checksum/deduplication
Document parsing
Chunking
Embeddings
```

### Expense plugin

Owns:

```text
Expense
ExpenseDocument
ExpenseApproval
ExpenseEvidence
ExpensePolicy
Expense Agent
Expense-specific policy/evidence interpretation
Manager approval workflow
Expense notifications
```

### Redis

Used for derived/hot artifacts such as:

```text
normalized policy snapshots
parsed expense evidence
```

It is not the source of truth for the business expense or immutable policy record.
